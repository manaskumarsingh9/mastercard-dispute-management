The decision recommendation (Agent 4) was never meant to be a separate optional phase sitting after argument generation. It sits **between enrichment and argument generation**. The logic is:

You cannot recommend whether to challenge until you have **both sides** of the story — issuer's case AND the merchant's enriched evidence. Only then does Agent 4 have enough to make a meaningful recommendation. If it only had the issuer's side, it would be one-sided and potentially misleading.

---

So the corrected case detail flow looks like this:

**Step 1** — Merchant clicks a claim row on the dashboard. Sees all issuer-side data and the Agent 1 summary. This is instant — pre-loaded at ingestion.

**Step 2** — Merchant clicks "Enrich". Evidence engine calls the relevant PSP, delivery partner, and card network APIs. Agent 2 selects the strongest evidence. Agent 3 produces a summary of the merchant's side. Full picture now exists.

**Step 3 (optional, configurable)** — If the merchant has Agent 4 enabled in settings, it now runs. It has both the issuer's case and the merchant's enriched evidence. It recommends whether to challenge or not — and how strong the case is.

**Step 4** — Merchant reviews everything and decides. If they choose to challenge, argument generation proceeds.

That is a much more precise and intelligent design for Agent 2. Let me reflect it back fully:

---

Agent 2 is not just a selector — it is an **evidence strategist**. It has two sequential tasks:

**Task 1 — Evidence planning (before calling the evidence engine)**

Agent 2 reads the issuer's claim, reason code, and any unusual details the customer has reported. It then decides what evidence would be needed to win this specific case. It starts with the template for that dispute code type as a baseline, but it reasons beyond the template. If the customer has raised something unusual — say, they claim the product was defective in a specific way — Agent 2 may determine that a delivery photo, a product usage log, or a service confirmation record would strengthen the case, even if those are not in the standard template. It then instructs the evidence engine on exactly what to fetch and from which sources.

**Task 2 — Evidence verification and annotation (after the evidence engine responds)**

Once the evidence engine returns its results, Agent 2 does not just pass them forward blindly. It verifies whether what came back matches what was requested. It then produces an annotated evidence map — clearly marking which key pieces of evidence were successfully retrieved and which are missing or incomplete. This annotated map travels with the case from this point forward. Every downstream agent — Agent 3a for summarisation, Agent 4 for recommendation, and Agent 3b for argument generation — uses this map to understand the strength of the evidence position before doing their work.

---

This also means the recommendation Agent 4 gives is grounded in reality. If the annotated map shows that two critical pieces of evidence could not be fetched, Agent 4 factors that into its recommendation. It is not just assessing the quality of what was found — it is also assessing the significance of what is missing.

Perfect. That completes the picture for Agent 2 cleanly.

So the full enrichment flow is:

**Automated first** — Agent 2 plans what is needed, instructs the evidence engine to make all relevant API calls, then verifies and annotates the results regardless of whether every call succeeded or not.

**Transparent to the user** — After enrichment completes, the merchant sees the full annotated evidence map. Green for what was successfully fetched, and clearly flagged for what could not be retrieved automatically.

**Manual top-up as an option** — If the merchant sees gaps in the evidence and believes they can fill them — by contacting a PSP, delivery partner, or any other source directly — they can upload those manually. This uploaded evidence then joins the annotated map alongside the automatically fetched evidence.

**Everything downstream uses the final map** — Agent 4's recommendation and Agent 3b's argument generation both work from the complete evidence picture, including anything the merchant uploaded manually. The annotated map always reflects the current state of evidence regardless of how it was obtained.

---

This is actually a very strong product design decision. It means the system never blocks the merchant due to an API failure. The automated path is always attempted first, the gap is made visible, and the human has the final say on whether to fill it. The AI's job at every step is to inform and assist — not to gatekeep.
